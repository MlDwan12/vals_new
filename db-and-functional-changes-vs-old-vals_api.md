# Изменения БД и функциональности vals_new vs старый vals_api

Сводка содержательных различий между новым бэкендом (vals_new, этапы 0–7 по §10 ТЗ) и старым
`vals_api`. Не включает процессные детали (кто/когда ревьюил, тесты, коммиты) и разовый перенос
данных (ETL этапа 7) — только то, что реально изменилось в схеме БД и в поведении приложения, и
почему.

## Схема БД — сводная таблица трансформаций

| Было (vals_api) | Стало (vals_new) | Почему |
|---|---|---|
| Три разных стиля имён колонок (`"createdAt"`, `date_create`, `created_at`) | Единый `snake_case` везде, в коде — `createdAt`/`updatedAt` через `name:` | Нормализация схемы (этап 1) |
| `timestamp` (без timezone) на большинстве таблиц | `timestamptz` везде | Прод хранит время в `Etc/UTC`; `timestamptz` даёт корректный момент времени без сдвига |
| `cases.slug` — без индекса | `UNIQUE` | Найденный пробел старой схемы |
| `articles`/`cases` — нет индекса на `date_published`/`priority` | Индексы добавлены | Производительность выборок публикации |
| `clients` — нет индекса на `primary_phone`/`primary_email` | Индексы добавлены | Поиск/дедуп клиентов |
| `client_leads` — нет индекса на `phone_normalized`/`email_normalized` | Индексы добавлены | Дедуп заявок |
| `service_to_case` — FK несимметричны (`service_id` блокирует удаление, `case_id` — нет) | Обе FK `ON DELETE CASCADE` | Баг старой схемы, дамп подтвердил |
| `article_authors.article_id`/`case_authors.case_id` — `ON DELETE RESTRICT` | `ON DELETE CASCADE` | `RESTRICT` при обязательном ≥1 авторе гарантированно блокировал удаление **любой** статьи/кейса — реальный 500-баг, найден живьём на этапе 3 |
| `clients.merged_into_client_id` — колонка без FK | `FK ... ON DELETE SET NULL` | Целостность self-ссылки при слиянии клиентов |
| `audit_logs` — по 2 одинаковых индекса на `user_id`/`action`/`created_at` | По одному | Устранён дубль |
| `media` и `image_lib` — две отдельные таблицы | Объединены в одну `media` | См. раздел «Медиа» ниже |
| `users` — без `created_at`/`updated_at`/`is_active`, без ограничения на `role` | Добавлены `created_at`/`updated_at`/`is_active`, `CHECK` на `role` (не отдельный enum — проще расширять) | Этап 2 (auth) |
| Сессий/refresh-токенов в БД не было | Новая таблица `refresh_sessions` (jti unique, userId FK CASCADE, fingerprint, expiresAt, revokedAt) | Ротация и отзыв refresh-токенов |
| `client_leads` — нет статуса доставки в Bitrix | Добавлены `status`/`retryCount`/`nextRetryAt`/`bitrixError` | Заявка больше не теряется при недоступности Bitrix (см. ниже) |
| `tariffs.is_popular`/`order_index` — единственный домен с колонками наружу в snake_case (без camelCase-маппинга) | `isPopular`/`orderIndex` — camelCase, как везде | Осознанная точечная правка контракта (см. ниже) |
| — | `cases.industry` остался `jsonb`-массивом свободных строк, без FK на `industries` | Так было и в старом коде — два независимых механизма, функциональность сохранена как есть |
| `industries` — без `slug` | Добавлен `slug` (nullable, unique) + публичные `/industries/published` и `/industries/info/:slug` | Пересмотрено 2026-08-19: ТЗ §2 явно требует «публичные страницы по slug» у отраслей — решение пользователя реализовать по ТЗ, а не по факту старого кода/дампа (расхождение было замечено при сверке дока с ТЗ). `slug` nullable — старые/непубликуемые отрасли без URL; уже заданный slug нельзя обнулить через PATCH (см. ниже) — иначе освободившийся slug мог достаться другой отрасли, и исходная безвозвратно теряла бы свою страницу |

## Общий контракт ответа/ошибок

- **`status` в конверте ответа теперь честный HTTP-код**, не захардкоженный `200` — было решением по
  открытому пункту ТЗ §4.
- **Коды ошибок (`ErrorCode`) теперь осмысленные**, не общий `HTTP_ERROR`. Изначально покрывались
  основные статусы; позже добавлены `413 PAYLOAD_TOO_LARGE` и `503 SERVICE_UNAVAILABLE` — раньше оба
  падали в `INTERNAL_ERROR`, хотя реально возникают в приложении (413 — превышение лимита загрузки
  файла, 503 — недоступность БД/Meilisearch).
- Дубли уникальных полей (`slug`/`name` у `articles`/`cases`/`employees`/`tags`/`services`/
  `industries`) раньше падали сырым `500` — теперь понятный `409 CONFLICT`.
- Нарушение FK при удалении используемой сущности (категория услуги, тег, сотрудник) раньше давало
  сырой `500` — теперь понятный `400 VALIDATION_ERROR` с текстом ошибки.
- Создание FAQ/шагов/тарифов и т.п. со ссылкой на несуществующего родителя (`serviceId`/`articleId`/
  `caseId`) раньше падало на FK сырым `500` — теперь явная проверка существования, `400
  VALIDATION_ERROR` с id.
- `ILike`-поиск (`clients`, затем `articles`/`cases`/`services`/`media`) не экранировал спецсимволы
  `%`/`_` — поиск `?search=%` буквально совпадал со всем подряд, `_` в легитимном вводе (например,
  `john_doe@...`) трактовался как wildcard. Добавлено экранирование во всех перечисленных местах.

## Auth и роли

- **Сессии — в БД** (`refresh_sessions`), с ротацией и обнаружением реюза: повторное использование
  уже отозванного refresh-токена теперь гасит **все** сессии пользователя (детект компрометации) —
  такого механизма в старом коде не было.
- **CSRF-защита по `Origin` — глобальная**, на все mutation-методы через `CsrfOriginGuard`. В старом
  коде была навешана вручную по отдельным роутам (`DomainRestrictionGuard`).
- **`isActive`** — новое поле, деактивированный пользователь получает 401 на следующем login/refresh.
- Rate limit на `/auth/login` — два независимых лимита (по IP + по нормализованному username), в
  дополнение к глобальному дефолту throttler'а.
- Куки авторизации — единая функция выставления/очистки, используется во всех местах (login/refresh/
  logout). В старом коде — три разных набора опций (разный `sameSite`, местами без `maxAge`).
- Нормализация username — теперь и при create, и при update (в старом коде — баг, применялась только
  при create).
- `users`: генерик `BaseCrudController`/`BaseCrudService` не перенесены (архитектурный запрет, не
  функциональное отличие само по себе, но повлияло на набор реально работающих проверок).
- **Починена реальная дыра в контроле доступа**: в старом коде `POST /admin/users` (генерик-роут от
  `BaseCrudController.create()`, `@Roles(...CONTENT_ROLES)`) существовал **одновременно** с тремя
  специфичными эндпоинтами (`/admin/users/{content-managers,client-managers,admins}`, каждый со своей
  ролью создателя). Это значило, что `content_manager` мог создать пользователя с любой ролью через
  генерик-роут в обход ограничений специфичных эндпоинтов (например `createAdmin`, доступный по
  замыслу только `developer`). В vals_new генерик-роут не существует в принципе — обойти ролевые
  ограничения нечем.

## Articles / Cases

- `GET /admin/cases/:id` в старом коде (через `BaseCrudService.findById`) отдавал сущность **без
  единой relation** (authors/tags/services/faq — все `undefined`); реальное редактирование
  использовало отдельный `GET /admin/cases/slug/:slug` с raw-SQL. В vals_new оба пути отдают один и
  тот же полный ответ со всеми связями.
- В старом raw-SQL-ответе кейса `services` был просто `serviceIds: number[]`, тогда как
  `authors`/`tags` — полные короткие объекты (несогласованность самого старого кода). В vals_new —
  единообразные короткие DTO для всех связей.
- Meilisearch/reindex логика вынесена целиком в отдельный этап 6 (поиск), не размазана по каждому
  контентному модулю, как фактически было в старом коде.
- Фильтрация по `authorSlug`/`tagSlug` теперь через подзапрос, не теряет статью/кейс с несколькими
  авторами/тегами (в старом подходе `andWhere` на join-алиасе мог обрезать остальные связи записи).

## Services / Tariffs / Tags / Employees / Industries

- **Slug тегов** — явное поле от клиента (выровнено с `articles`/`cases`), не авто-генерация
  транслитерацией + идемпотентный create по имени, как в старом коде.
- **`GET /admin/tags`** — без пагинации, с `articlesCount`/`casesCount`, как в старом коде (условная
  пагинация оказалась нереализуемой поверх общего DTO, да и не была нужна — старый фронт эти
  параметры никогда не отправлял).
- Удаление тега/сотрудника при FK-конфликте: старый комментарий в коде утверждал, что `tag_id` —
  `ON DELETE CASCADE` и конфликт невозможен в принципе; по факту в реальной схеме — `NO ACTION`.
  Комментарий был неверен, теперь есть перехват с понятным сообщением.
- **`tariffs.isPopular`/`orderIndex`** — в старом коде отдавались наружу буквально как
  `is_popular`/`order_index` (единственный домен без camelCase-маппинга). В vals_new — camelCase
  везде, осознанная точечная правка контракта (как честный `status`/коды ошибок).
- `periodsIds` (опечатка старого API) переименован в `periodIds`.
- `CreateTariffPeriodDto.basePrice` — поле, которого никогда не было в реальной entity
  `tariff_periods` (мёртвое, никогда не сохранявшееся); в vals_new убрано из DTO, `ValidationPipe`
  теперь возвращает 400 на это поле, а не молча игнорирует.
- Старый `TariffsService` требовал `periodsIds` через `@ArrayNotEmpty()`, из-за чего ветка
  «синтетический цикл по умолчанию» была фактически мертва (недостижима). В vals_new `periodIds`
  опционален — ветка синтетического цикла реально работает.
- Старый код на случай отсутствия периодов шёл в БД за периодом с захардкоженным `id: 1`
  («месячный», в предположении что он всегда существует). В vals_new синтетический цикл собирается
  без обращения к `tariff_periods` вообще — хрупкое место устранено.
- `discountPercent` тарифного периода — раньше без `@Min(0)`/`@Max(100)`, значение >100 давало
  отрицательную цену за месяц, реально сохранённую и публично отдаваемую. Теперь валидируется.
- **Отрасли (`industries`) получили `slug` + публичную страницу** (`GET /industries/published`,
  `GET /industries/info/:slug`) — этого не было ни в старом `vals_api`, ни изначально в vals_new,
  хотя ТЗ §2 явно этого требует (пересмотрено 2026-08-19, решение пользователя). `slug` nullable —
  не у каждой отрасли обязана быть публичная страница; но уже заданный `slug` нельзя обнулить через
  `PATCH` (отдельная валидация `ValidateIf` вместо `IsOptional`) — иначе освободившийся уникальный
  slug мог достаться другой отрасли, и исходная безвозвратно теряла бы свой URL.

## Медиа (media + image_lib → media)

- **Две старые таблицы/подсистемы объединены в одну.** `image_lib` дропнута миграцией, все записи
  мигрированы (см. ETL этапа 7 отдельно) в единую `media`.
- **Путь роутов — `/admin/media`** (не старый `/media` без admin-префикса) — консистентно с
  остальными доменами, изменение контракта.
- **Ответ на upload — массив созданных записей** (`MediaResponseDto[]`), не `{success:true}`, как
  было у старого `/media` (тот вообще не возвращал данные о загруженном файле — пробел старого
  контракта).
- **Лимит размера — бюджет на запрос**, не фиксированный per-file: `TOTAL_UPLOAD_BUDGET_BYTES = 10
  МБ` на весь upload, `MAX_SINGLE_FILE_BYTES = 1 МБ` — потолок на файл. Старые системы: `media` —
  200 КБ жёстко, `image-lib` — 5 МБ жёстко.
- **Проверка сигнатуры файла (magic bytes WEBP)**, не только `mimetype` (заявляемый клиентом и
  подделываемый) — в старом `media.service.ts` такой проверки не было вовсе.
- **Удаление — БД первая (источник истины) + `logger.warn` при ошибке unlink**, не тихий `catch {}`,
  как было в старом `media.service.ts`.
- Runtime-проверка «не вышли ли за `uploads`» (была в старом `image-lib.service.ts`,
  `safeResolveUploadPath`) не перенесена — путь всегда строится только из генерируемого сервером
  `uuid.webp`, traversal структурно невозможен, а не предотвращается проверкой постфактум.
- Файлы при слиянии таблиц **не переименовываются** — имя (basename, уже уникальный UUID в обеих
  старых таблицах) упоминается как текст внутри контента статей/кейсов и `employees.photo_url`, не
  как FK — переименование сломало бы уже опубликованный контент.

## Заявки и клиенты (Bitrix)

- **Порядок сохранения изменён**: раньше сначала шёл запрос в Bitrix, при недоступности CRM заявка
  терялась целиком. Теперь заявка **всегда** сохраняется первой (`status: pending`), доставка в
  Bitrix — полностью асинхронная (планировщик), либо ручной retry.
- **Новый механизм доставки с ретраями**: `status`/`retryCount`/`nextRetryAt`/`bitrixError` на
  `client_leads`, экспоненциальный backoff (1мин→5мин→30мин→2ч→6ч), после 5 неудач —
  `status: failed`, дальше только вручную. Такого механизма в старом коде не было.
- **Защита от спама** — `@Throttle` (5/мин по IP) + honeypot-поле `website` в DTO (заполнено → тихий
  201, заявка не обрабатывается). Публичная форма старого API была вообще без защиты.
- **Автослияние клиентов** — перенесено функционально 1:1 (тихое автослияние при конфликте
  телефон/email в одной заявке, id поменьше побеждает), но теперь с `logger.warn` на каждое слияние
  (в старом коде — тихо, без следа в логах).
- **Тарифные лиды — структурированный снапшот** (`payload.tariff`: serviceName/tariffName/
  periodMonths/pricePerMonth/totalPrice), посчитан один раз при приёме заявки — раньше это
  восстанавливалось regex-парсингом из текстового комментария Bitrix постфактум.
- **Починенный баг**: `UF_TARIFF_NAME`/`UF_TARIFF_PRICE` в Bitrix-пейлоаде тарифных лидов получали
  сырые `tariffId`/`periodId` вместо реального названия тарифа и цены.
- Ручной `retry` теперь проверяет текущий статус лида — раньше повторный клик (или retry уже
  доставленного планировщиком лида) создавал дубль в самом Bitrix CRM.
- `POST /bitrix` — путь **сохранён** (не переименован в `/leads`), это часть публичного контракта,
  фронт на проде уже шлёт сюда.

## Поиск (Meilisearch)

Поиска на Meilisearch в старом коде тоже не было единой картины — вот отличия от него:

- **FAQ индексируется по всем трём доменам** (article_faq/case_faq/service_faq), не только
  `service_faq`, как в старом коде — это следствие того, что FAQ в новой схеме уже существует у всех
  трёх сущностей (принято ещё на этапе 3), не новая фича сама по себе.
- **Починенные баги старого поиска:**
  - Черновики/отложенные статьи и кейсы утекали в публичный поиск (не было фильтра по дате
    публикации при индексации) — теперь при unpublish/переносе даты в будущее документ удаляется из
    индекса.
  - Рассинхронизация префиксов id при удалении кейса (`case_{id}` при индексации, `caseEntity_{id}`
    при удалении) — кейсы никогда фактически не пропадали из индекса. В новом коде такого
    расхождения не может быть по построению.
  - При удалении статьи/кейса/услуги теперь удаляются и документы её FAQ из индекса — в старом коде
    ORM-каскад чистил БД, но не Meilisearch, осиротевшие FAQ-документы оставались навсегда.
- **Два ключа Meilisearch** вместо одного мастер-ключа: `MEILI_MASTER_KEY` (админские
  операции/индексация) и `MEILI_SEARCH_KEY` (только права `search`, публичный поиск).
- Индексация — синхронная при create/update/remove; ошибки Meilisearch только логируются, не роняют
  мутацию.
- Reindex — по одному admin-эндпоинту на домен, FAQ переиндексируется вместе с родителем (в старом
  коде был отдельный эндпоинт под `faq.module`).
- Приложение не падает при недоступном Meilisearch на старте — старый код падал здесь без обработки.

## Аудит

- В старом коде подсистемы аудита в этом виде не было. Новое:
  - Запись через `AuditInterceptor` (успешные мутации/logout) + `HttpExceptionFilter` (security-
    события вроде 401/403 — интерцепторы не видят исключения от guard'ов).
  - `AuditRetentionScheduler` — ежедневная чистка записей старше 180 дней.
  - Подавление повторных анонимных `ACCESS_DENIED` с одного IP в окне 60с — защита от заполнения
    аудита флудом неавторизованных запросов.
  - Починенный старый баг: `res.statusCode` читался до того, как Nest его выставлял — 201/204 в
    аудите были нечестными (записывались как 200). Теперь честные коды.
- Таблица `audit_logs` в проде (743 строки) — по решению пользователя **не перенесена**, журнал
  начат заново (исторический трейл под уже переименованные пути, не бизнес-данные).

## Дашборд

- Статистика — паритет со старым `DashboardStatsDto` (`articles/cases: {total,published,scheduled}`,
  `services: {total}`, `clients: {total,totalLeads}`), реализовано через явные `count()`-запросы
  вместо сырых SQL старого кода.
- Доступ — расширен на `ALL_ROLES` (все 4 роли), раньше не документирован отдельно как доменная
  группа.

## Изменения контракта API (пути/методы)

Найдены сверкой `GET /docs-json` (120 роутов) с эталонным `openapi.json` старого бека (129 роутов),
согласованы с пользователем как принятые, не восстанавливаются:

| Было | Стало |
|---|---|
| `/admin/client` (ед. ч.) | `/admin/clients` (мн. ч.) |
| `POST /admin/client` (ручное создание клиента админом) | Убран полностью — клиенты создаются только неявно через приём заявки |
| `PATCH /admin/client/{id}` | Убран — в старом коде `UpdateClientDto`/`CreateClientDto` были пустыми классами (`{}`), роут ничего реально не принимал (тот же класс мёртвого роута, что и у `image-lib`) |
| `GET /auth/logout` | `POST /auth/logout` |
